# Banking Data Warehouse: ETL, Star Schema and PL/pgSQL

A small but complete data warehouse for a retail bank's daily transaction feed. A Python ETL loads raw CSV
extracts into a staging area, PL/pgSQL stored procedures validate and transform the data, and a star
schema serves reports. Every run is logged, every rejected row keeps its reason, and every load is
reconciled, which is what application and production support teams check first when something breaks.

**Stack:** PostgreSQL 16 · SQL · PL/pgSQL (stored procedures and functions) · Python · psycopg · pytest · GitHub Actions

## How it works
```
CSV extract ──COPY──▶ stg.* (raw text) ──PL/pgSQL──▶ dw.dim_* + dw.fact_transaction ──▶ reporting view
                                           │
                                           ├─▶ dw.etl_reject  (row + reason)
                                           └─▶ dw.etl_run     (status, rows read / loaded / rejected)
```

| Layer | What it holds |
|---|---|
| `stg` | Raw daily extract loaded as text with `COPY`; truncated every run |
| `dw.dim_date` | Calendar with Indian fiscal year (Apr–Mar) |
| `dw.dim_customer` | **SCD Type 2**: a change in segment or city closes the old row (`valid_to`) and opens a new one |
| `dw.dim_account`, `dw.dim_branch`, `dw.dim_channel` | Type 1 dimensions |
| `dw.fact_transaction` | One row per valid transaction, with surrogate keys and a **point-in-time join** to the customer version valid on the transaction date |
| `dw.mv_monthly_branch_channel` | Materialized view for monthly branch and channel reports |
| `dw.etl_run`, `dw.etl_reject` | Audit log and rejected records |

**Validation rules** (in `dw.fn_load_fact_transaction`): duplicate IDs, already-loaded IDs (makes re-runs
safe), missing, non-numeric or non-positive amounts, future dates, invalid channels or directions, and
unknown accounts. `dw.sp_run_etl` wraps the load in an exception handler, so a failed run is marked
`FAILED` with the error message instead of leaving the warehouse half-loaded.

## Results (synthetic data)
| Run | Rows read | Loaded | Rejected | Time |
|---|---|---|---|---|
| Batch 1: Apr–Sep 2026 | 200,235 | 197,849 | 2,386 (all 6 planted problem types) | ~14 s |
| Batch 2: next day | 1,503 | 1,485 | 18 | ~0.5 s |

- Reconciliation passes for both runs: rows read = rows loaded + rows rejected.
- Batch 2 changed 116 customers; SCD Type 2 kept their history with exactly one current row each.
- Re-running a batch loads nothing new (idempotent).
- **Indexes:** a one-month account statement query drops from ~12 ms to ~0.07 ms (≈170× faster);
  a quarterly branch report goes from ~12 ms to ~3 ms (`benchmark.py`).

`analytics.sql` answers business questions: digital share of transactions by month (≈86%), top branches
by net inflow (window `RANK()`), dormant accounts, unusual transactions (above 3 standard deviations of an
account's average), running net flow per account, SCD history and a data-quality report per run.

## Run it
```bash
pip install -r requirements.txt
export DATABASE_URL=postgresql://postgres:postgres@localhost:5432/postgres
python generate_data.py --batch 1 && python generate_data.py --batch 2
python etl.py --init --batch 1 --as-of 2026-09-30
python etl.py --batch 2 --as-of 2026-10-01
psql "$DATABASE_URL" -f analytics.sql
python benchmark.py
pytest -v          # 9 end-to-end tests
```

## Porting to Oracle
The logic maps directly to Oracle PL/SQL: `CREATE OR REPLACE PROCEDURE … IS BEGIN … EXCEPTION WHEN OTHERS
THEN … END;`, `GENERATED ALWAYS AS IDENTITY` works in Oracle 12c+, `ON CONFLICT` becomes `MERGE`,
`FILTER (WHERE …)` becomes `SUM(CASE WHEN …)`, `GET DIAGNOSTICS` becomes `SQL%ROWCOUNT`, and `COPY`
becomes SQL*Loader or an external table. In an Oracle shop, the staging-to-warehouse step is what a tool
like ODI (Oracle Data Integrator) would orchestrate.

The data is synthetic (generated by `generate_data.py`); no real customer data is used.
